1. The products.parquet file seems to be the easiest source to integrate into this pipeline. Because parquet files have a columnar format that is enforced with a strict schema that makes sure that data integration is straightforward. It enforces the data types automatically. The profilling for the products.parquet file showed that no missing values were in the dataset and no fully duplicated rows. The structured coding of this file removes any need for coding complex algorithms to perform ETL and saves time from data cleaning.

2. The orders.json file shows the greatest risk of having problems with the schema integration. Becuase of JSON's semi-structured data format, with nested dictionaries that requires flattening before becoming a tabular format easily integratable into SQL formats. While customers.csv has the greatest risk of having data quality problems because of the profiling that revealed that the csv file had 3 duplicates and some missing values. The pipeline will fail if this was coerced into the SQL if the primary key constraint was not removed.

3. If this pipeline was built without even understanding or taking a look at any of the datasets, or making any data contracts and profiling, it would lead to data corruption or ingestion failures. If we assumed wrongly on the datasets, like for example, if customers.csv has a perfect customer_id uniqueness, a primary key constraint would have worked, but in our case, that was caught by the profiling step which led to the removal of that constraint in the SQL create schema file.

4. These tools eliminate the problem of only one coder having access to all the files needed for a project, it also removes the problem of the code working only on one machine. Git provides a history of all changes and could be rolled back to salvage previous code that may have been overwritten mistakenly. Virtual environments isolate the Python dependencies, preventing mismatched Python library versions from breaking projects. Containers package the database and system dependencies into self-sufficient units that run similary on any operating system, which makes the project run on any machine. Finally, having documentation allows other people to use and run the project in the intended way without room for error.
